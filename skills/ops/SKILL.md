# acli — Atlassian Cloud CLI

Drive Jira, Confluence, org admin, and Rovo Dev from the terminal. Auth-first, JQL-driven, confirmation-gated.

**Content creation/editing routes elsewhere** — `atlassian-kit:jira-content` (Jira Bug/Story/Task/Epic/Sub-task content) and `atlassian-kit:confluence-content` (Confluence Spec/PRD page content). They own the template standard and call into this skill's commands to execute. **Atlassian MCP is the fallback, not the default** — only for the closed list in [When acli can't](#when-acli-cant-fall-back-to-the-atlassian-mcp).

> ⚠️ **This applies even mid-flow inside another skill.** A different skill's instruction to "publish this to the tracker/backlog" (a PRD-writer, a code-review follow-up, a to-do capture) does NOT mean hand-build a description and fire `acli jira workitem create --description-file`/`--description` directly — that's exactly the flattened-plain-text failure this file warns about (real incident: PROJ-809, PROJ-806). Stop and load `atlassian-kit:jira-content` for the template shape first, whatever content standard the calling skill uses.

> ⚠️ **The same guard applies to comments.** If a comment task names or clearly matches one of the four templated types — status update, QA verification, blocker, decision record — that classification wins over any specific wording/format the user asked for ("bold BLOCKED label," exact bullets, anything) and over `jira-content` being unavailable this session. Load `atlassian-kit:jira-content` for the template shape first. If it's genuinely unreachable, don't ship a same-shaped draft that silently omits its required fields — say so explicitly to the user and name the missing field(s) (e.g. blocker's "impact if unanswered" line).

## Always first: auth gate

Two independent layers — global OAuth and per-product. A product can be authed even when the global profile is not. Check before any command.

```bash
acli jira auth status        # check BEFORE any jira command
acli confluence auth status
```

Not authed:
```bash
acli jira auth login --web                                              # OAuth, browser
echo "$TOKEN" | acli jira auth login --site SITE.atlassian.net --email me@x.com --token   # API token via stdin
```

> `--token` reads stdin only — never pass a token as a flag value. Token: https://id.atlassian.com/manage-profile/security/api-tokens

Full auth model + per-product details → `REFERENCE.md` § "Auth model".

## Core loop (Jira work items)

```bash
# 1. FIND — JQL is the selector for everything downstream
acli jira workitem search --jql "project = TEAM AND statusCategory != Done" --fields key,summary,status
acli jira workitem search --jql "..." --json     # parse | --csv export | --web open | --count | --paginate
# ⚠️ bare --json/--csv silently caps at ~30 rows (Jira's page size) — no error, no truncation notice. Verified 2026-07-24: 227 real matches, unpaginated --json returned exactly 30. Always --paginate, or cross-check the count against --count first — this applies to reads, not just pre-mutation previews.
# Always double-quote --jql and any interpolated file-path argument — JQL text searches can embed apostrophes/spaces (e.g. summary ~ "user's request") that break unquoted or single-quoted shell args.

# 2. INSPECT — ~80% fewer tokens than raw JSON:
acli jira workitem view KEY-123 --json | python3 ${CLAUDE_SKILL_DIR}/scripts/adf2md.py

# 3. CREATE — anything multi-section goes through md2adf.py (--description wraps plain text into ONE literal paragraph — see "Description format" below)
python3 ${CLAUDE_SKILL_DIR}/scripts/md2adf.py desc.md -s "Summary" -p TEAM -t Task > /tmp/wi.json && acli jira workitem create --from-json /tmp/wi.json
acli jira workitem create --summary "X" --project TEAM --type Task --assignee @me   # OK ONLY when there's no multi-section description
acli jira workitem create-bulk --from-csv issues.csv       # or --from-json; --generate-json scaffolds input

# 4. MUTATE — target by --key | --jql | --filter
acli jira workitem transition --jql "project = TEAM AND status = 'To Do'" --status "In Progress" --yes
# ⚠️ no acli-native way to list valid transitions read-only — `--list` was removed (still gone in 1.3.40-stable). See "When acli can't" for the MCP fallback; otherwise an invalid target status fails loud per-item at fire time (unless you pass --ignore-errors), it doesn't silently skip.
acli jira workitem edit --key "KEY-1,KEY-2" --summary "..." --labels a,b
# ⚠️ edit --description REPLACES the whole description. Append safely: bash ${CLAUDE_SKILL_DIR}/scripts/acli-edit.sh KEY notes.md
# ⚠️ Templated comment guard applies here too (see top of file) — no "user specified exact wording" exception, no "jira-content unavailable" exception. Command below is ONLY for a note that is none of the four templated types.
python3 ${CLAUDE_SKILL_DIR}/scripts/md2adf.py note.md > /tmp/note.json && acli jira workitem comment create --key KEY-1 --body-file /tmp/note.json   # plain ad hoc note only — see guard above
acli jira workitem comment create --key KEY-1 --body "..."   # OK ONLY for a single plain sentence
# comment update needs --body-adf FILE (its --body/--body-file are plain-text-only, no ADF auto-detect):
acli jira workitem comment update --key KEY-1 --id 10001 --body-adf /tmp/note.json
acli jira workitem assign --key KEY-1 --assignee @me       # @me | default | email
```

`@me` self-assign, `default` project default. ⚠️ `assign --assignee` resolves `@me`/`default`/**email** only — a raw **accountId silently UNassigns** (acli prints "unassigned" and clears it; verified). For a known accountId, use `bash ${CLAUDE_SKILL_DIR}/scripts/acli-assign.sh KEY ACCOUNT_ID` instead — it routes through `edit --from-json`, which resolves accountId correctly (verified 2026-07-15 against two different accounts; the bug is scoped to the `assign` subcommand only, not acli as a whole). Resolving an accountId from a privacy-hidden email in the first place is still MCP-only → [When acli can't](#when-acli-cant-fall-back-to-the-atlassian-mcp). `--generate-json` scaffolds any complex create/edit/link input. Per-flag tables → `REFERENCE.md`.

**Description format:** Jira `description`/comment `body` is ADF. Flags (`--description`/`--body`) wrap plain text into **one literal ADF paragraph — no markdown parsing.** `## heading`, `**bold**`, numbered/bulleted lists typed straight into the flag show up in Jira as those literal characters, not formatting — this is the #1 cause of a ticket or comment rendering as garbled plaintext. Use the flag only for a single unformatted sentence. Anything with headings/lists/bold/multiple sections needs a real ADF object: write Markdown and run `python3 ${CLAUDE_SKILL_DIR}/scripts/md2adf.py desc.md` (bare doc mode — omit `-s/-p/-t` for a comment/append body). Read it back with `${CLAUDE_SKILL_DIR}/scripts/adf2md.py`. `md2adf.py` parses GFM markdown tables (`| a | b |` + `|---|---|`) into real ADF `table` nodes (fixed 2026-07-15, `ISSUES.md` Issue 5; regression test: `scripts/test_md2adf.py`). It still only knows the Markdown subset in its own docstring — a description with node types outside that (e.g. `expand`, `panel`, an `extension`/macro) won't round-trip through a full-body replace. Count structural nodes in the current description before any full-body replace on an existing ticket that might carry one of those: `acli jira workitem view KEY --json | python3 ${CLAUDE_SKILL_DIR}/scripts/adf-node-diff.py -`; if `expand`/`panel`/`extension` count > 0, edit around it (`acli-edit.sh --replace-section` on an unaffected section) or patch the raw ADF directly instead of round-tripping through Markdown. After a full-body write, diff the intended patch against what's now live — `adf-node-diff.py intended.json <(acli jira workitem view KEY --json)` — a `byte-exact match: NO` on a write that should've been a pure passthrough is the signal something got silently dropped. Attachment differs by command: `workitem create/edit` → `--from-json`; `comment create` → `--body`/`--body-file` (auto-detect plain vs. ADF); `comment update` → dedicated `--body-adf FILE` flag. Confluence body is storage-format XHTML. Rules + GOOD/BAD → `REFERENCE.md` "Description & body formats" + `examples/`. **Content standard (what a description/comment should say, AC format, etc.) is not this skill's concern** — that's `atlassian-kit:jira-content` § `templates/` (Jira) or `atlassian-kit:confluence-content` § `templates/` (Confluence).

## Bulk-mutation safety

Mutating bulk ops (`edit`, `transition`, `assign`, `delete`, `clone`, `link create`) accept `--jql`/`--filter` and a `--yes` confirmation skip.

1. **Preview the set first** — run `search` with the *exact same* `--jql` and `--count` before any `--yes` mutation. The JQL selects what you'll change; verify it.
2. `--yes` skips the interactive confirm — only after the preview matches intent.
3. `--ignore-errors` continues past per-item failures. Default OFF — read the result summary; a partial failure must be loud, not swallowed. Sub-tasks can't be archived/deleted on their own (✗ "Issue is a subtask"), so a key-list `archive`/`delete` batch reports partial failures — archive/transition the parent or the sub-tasks separately.

## Create safety

`create`/`create-bulk` are outward-facing too — but unlike the mutations above they have no JQL set to preview, so preview the **payload itself** before firing.

1. **Render what you're about to send.** For a `--from-json` create, round-trip it first: `python3 ${CLAUDE_SKILL_DIR}/scripts/md2adf.py desc.md -s "..." -p PROJ -t Bug > /tmp/wi.json && python3 ${CLAUDE_SKILL_DIR}/scripts/adf2md.py /tmp/wi.json` prints a readable card — `(new) <type>`, project, labels, and the full description. Eyeball it, *then* `acli jira workitem create --from-json /tmp/wi.json`. `${CLAUDE_SKILL_DIR}/scripts/acli-new.sh` (the one-step shortcut) does the same round-trip internally — call it once with `--dry-run` first to eyeball the same card, then call it again without the flag to actually create.
2. For `create-bulk`, `--generate-json` first (or render one row) and read it back before the batch — a bad template multiplies across every row. ⚠️ `create-bulk --from-json` **rejects rich-markdown descriptions** (headings/code fences/backticks/newlines) → ✗ "request body is missing or invalid". Pattern that works: bulk-create with **short placeholder** bodies, then set the real description per ticket with `bash ${CLAUDE_SKILL_DIR}/scripts/acli-set-desc.sh KEY desc.md` (verified PROJ-558..566).
3. **Resolve metadata, don't hardcode it.** Project/type/priority/labels/assignee must match the target project; `--generate-json` emits the schema the project actually accepts — scaffold from it when unsure of a type or field. The templates ship `projectKey:"PROJ"` as a personal default — swap it (or pass `-p`) for any other project. On an unknown project/type/field acli fails: fix it, never strip the field and retry.

## Confluence & admin write safety

`confluence blog create`, `confluence space create`, and every `admin user` lifecycle command (`activate`/`deactivate`/`delete`/`cancel-delete`) have **no native `--yes`/confirm flag** — unlike `jira workitem edit/transition/assign`, nothing in acli itself stops a bad target from firing. This skill supplies the safety net manually:

1. **Confluence blog/space create** — same rule as [Create safety](#create-safety) above: no JQL set to preview, so preview the **payload** instead. Render the body/title/space before sending; for `--from-file`/`--from-json`, read the file back and eyeball it first.
2. **`admin user` lifecycle ops are the highest blast-radius command in this plugin** — deactivate/delete act on real accounts, `--from-file` accepts a bulk target list, and `--ignore-errors` continues past per-account failures with none of it caught by acli itself. Before running any `admin user deactivate|delete|cancel-delete`:
   - Resolve and print the **exact target list** (emails/accountIds) and get explicit user go-ahead — the missing native confirm flag is this skill's job to backfill, not a license to skip confirmation.
   - Leave `--ignore-errors` off by default, same as [Bulk-mutation safety](#bulk-mutation-safety) — a partial failure across accounts must be loud, not swallowed.
   - `activate`/`cancel-delete` are recoverable; `deactivate`/`delete` are not (or not cheaply) — weight the confirmation ask accordingly.

## When acli can't (fall back to the Atlassian MCP)

acli is the default. A small, closed set of operations genuinely need `mcp__plugin_atlassian_atlassian__*` (or the Jira UI) — this list is the full accounting, not a sample. If you're about to name an MCP tool anywhere in this plugin for something not on this list, check `REFERENCE.md`'s command surface first and add the row here if it's genuine, don't let it live undocumented in `jira-content`/`confluence-content`. Reach for the MCP **only** here:

> **Status, 2026-11-19:** the Atlassian MCP is unavailable in this environment (its token is blocked and OAuth is not authorized). Until it returns, the three read gaps below (accountId, transitions, issue-type metadata) go through
> `scripts/acli-rest-get.py`, the write gaps through `scripts/acli-rest-write.py`, and the rest is UI-only.
>
> **`acli-rest-get.py`** is GET-only and takes no flags. It reads site and email from `acli jira auth status` and a token from `~/.claude/atlassian.env` (mode 600; keys `ACLI_REST_READ_SITE`, `ACLI_REST_READ_EMAIL`, `ACLI_REST_READ_TOKEN`): a scoped API token with `read:jira-work` and `read:jira-user` (an API token, scoped or classic per product, created by the operator; the `api confluence <PATH>` raw reads use the write trio `ACLI_REST_WRITE_SITE`/`ACLI_REST_WRITE_EMAIL`/`ACLI_REST_WRITE_CONFLUENCE_TOKEN` instead). The site and email in the file must match acli's, or the script stops with `FATAL`. Never read, create or print that file or the token yourself. Do not name an MCP tool that is not in the session. `api <jira|confluence> <PATH>` is its raw read-only read for ad-hoc endpoints (jira `/rest/api/3/*`, confluence `/wiki/api/v2/*`); every command is GET-only by construction.
>
> **`acli-rest-write.py`** ships the write gaps below (live-tested pending). Every write is two commands: `plan <op> ...` reads state, shows the preview and writes a request file with a confirm hash; `apply <request-file> --confirm <hash>` re-checks everything before sending, then reads the write back: exit 0 (verified), 1 (refused, nothing sent), 2 (sent, server rejected 4xx), 3 (sent, unverified — never re-run `apply` before checking). Tokens: `ACLI_REST_WRITE_SITE/EMAIL/<JIRA|CONFLUENCE>_TOKEN` in the same mode-600 env file. **All first live writes are blocked by missing site permissions (admin matter), so agents stop after the preview.**
>
> **Atlassian MCP v2.** Tool names below are v2 (per its [supported-tools page](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/supported-tools/), checked 2026-11-12). v2 call shapes come from Atlassian's own v2 skills in [atlassian/atlassian-mcp-server](https://github.com/atlassian/atlassian-mcp-server/tree/b74220d41142fae52b4f680c805b2ab81050991a/skills) at `b74220d`, the commit the official plugin pins. Those are examples, not a live call; none of this was run here.
>
> - **v1 names:** `createConfluenceContent`/`updateConfluenceContent`/`getConfluenceContent` were `createConfluencePage`/`updateConfluencePage`/`getConfluencePage`; `listJiraIssueTransitions` was `getTransitionsForJiraIssue`; `listJiraProjectIssueTypesMetadata` was `getJiraProjectIssueTypesMetadata`; `listJiraProjects` was `getVisibleJiraProjects`; `listConfluenceSpaces` was `getConfluenceSpaces`. The v1 names are not on the v2 tool list, and for the Confluence renames Atlassian says the old names survive only as search synonyms, not callable tools. v1 connections switch to v2 tools on 2027-03-01 (per Atlassian's [v1→v2 upgrade page](https://support.atlassian.com/atlassian-ai-gateway/docs/how-to-upgrade-from-atlassian-mcp-v1-to-atlassian-mcp-v2/)).
> - **Deferred tools:** on the default v2 endpoint only tools marked `Primary` are listed to the agent (`getAccessibleAtlassianResources`, `getJiraIssue`, `createJiraIssue`, `editJiraIssue`, `createConfluenceContent`, `updateConfluenceContent`, `getConfluenceContent` are). The rest named in these docs (`listJiraIssueTransitions`, `listJiraProjects`, `listJiraProjectIssueTypesMetadata`, `getJiraIssueTypeMetaWithFields`, `lookupJiraAccountId`, `listConfluenceSpaces`) are deferred. Run one as `executeRead(name="<tool>", cloudId="<id>", inputs={...})`: `cloudId` is top-level, `inputs` is a flat object, and some clients expose a single `execute` instead of the three tiers. Use `discover` when you don't know a tool's name or aren't sure of its inputs: it returns the exact `name` and `inputs`. Skip it for a tool you already have as Primary. None of the six writes; don't send a write through `executeWrite`/`executeDestructive` without the same preview-and-confirm the acli writes get.
> - **Wrong parameter names can fail silently on v2:** Atlassian says an `execute` call drops parameters it doesn't know and still succeeds, so a v1 name such as `searchString` is just ignored. Whether Primary tools behave the same is not stated, so treat them the same way. Use the v2 shapes in these docs, or the live schema / `discover` where they say so. After any MCP Jira write (`createJiraIssue`, `editJiraIssue`), read the issue back with `getJiraIssue` and check each field you sent; the rules are in `atlassian-kit:jira-content` Step 5b.
> - **Confluence contract:** `getConfluenceContent` returns only a summary unless you pass `detail="full"`, and that response carries the `snapshotToken` that `updateConfluenceContent` requires. Create/update take `body={"format": ..., "value": ...}` instead of v1's `contentFormat` + string `body`; create also takes `contentType` and a `parent` object. Atlassian's examples show only `"markdown"` as a format, so confirm `"adf"` is accepted in the live schema before any ADF write.
> - **Endpoint:** the official Atlassian plugin connects to `https://mcp.atlassian.com/v2/mcp`, so `executeRead` is the only path for plugin users. `https://mcp.atlassian.com/v2/mcp?tools=all` lists every tool flat, but only on a server you configure yourself, and such a server does not get the `mcp__plugin_atlassian_atlassian__` prefix these docs use (see `../../README.md`); don't tell the user to reconnect just to reach one tool. If a tool is not in your tool list, deferral is why; it is not missing.
> - **Not in Atlassian's examples (check the live schema):** `listJiraIssueTransitions` inputs, `editJiraIssue` fields, the `createJiraIssue` description format, where `environment`/`versions` go on create, ADF bodies, and response shapes.

MCP `editJiraIssue` is the fallback.
- **Resolving an accountId** from a name/privacy-hidden email in the first place — acli has no lookup command for this. → `python3 ${CLAUDE_SKILL_DIR}/scripts/acli-rest-get.py find-user "<name|email prefix>"`. Best effort, two limits: one page of at most 50 users, and Jira searches at most 1,000 users, so an empty result is not proof the user does not exist. Whether a privacy-hidden email matches is not verified. Or MCP `executeRead(name="lookupJiraAccountId", cloudId="<id>", inputs={"query": "<name|email>"})` (v1: `lookupJiraAccountId cloudId:<id> searchString:"<name|email>"`). (Once you have the accountId, assigning it is **not** an MCP case anymore — `bash scripts/acli-assign.sh KEY ACCOUNT_ID` does it via acli's own `edit --from-json`, which resolves accountId correctly; only the dedicated `assign --assignee` subcommand mis-resolves it.)

- **fixVersion / release versions** — acli has no `version create`, `edit --from-json` rejects `fixVersions`, and `search --fields fixVersions` errors (read it via `view --json` + parse). → read via `view --json` + parse; writes go through `${CLAUDE_SKILL_DIR}/scripts/acli-rest-write.py`: `plan version-create` for a new version, `plan version-edit --id <id> --description/--released/--archived/--release-date` (at least one field besides `--id`) and `plan version-delete --id <id>` (verified by a 404 read-back; `--delete-fixed-issues|--delete-affected-issues true`, `--move-fixed-to|--move-affected-to ID` as escapes) for the lifecycle ops.
- **Issue-type metadata for a project** — no acli command exposes which fields/issue-types a project accepts at create time (`jira field` only manages custom fields; `create --generate-json`'s schema doesn't vary by project/type). → `python3 ${CLAUDE_SKILL_DIR}/scripts/acli-rest-get.py createmeta PROJ` lists the issue types; `python3 ${CLAUDE_SKILL_DIR}/scripts/acli-rest-get.py createmeta PROJ <issueTypeId>` lists that type's fields. Or MCP `executeRead(name="listJiraProjectIssueTypesMetadata", cloudId="<id>", inputs={"projectIdOrKey": "PROJ"})` (v1: `getJiraProjectIssueTypesMetadata`) (singular — one project per call) to list issue types, then `executeRead(name="getJiraIssueTypeMetaWithFields", cloudId="<id>", inputs={"projectIdOrKey": "PROJ", "issueTypeId": "<id>"})` for that type's actual field list, when a create rejects and you need to confirm why.
- **Priority / Environment / Affects-Version at *create* time** — none of these three appear in `create --generate-json`'s schema or `--help` output, for any project/type (verified empirically). → create the issue plainly with acli, then `plan issue-set` / `apply` through `${CLAUDE_SKILL_DIR}/scripts/acli-rest-write.py` (`--priority`, `--environment-adf`, `--add-affects-version`) on it; or MCP `createJiraIssue`: on v2 `priority` is a top-level string and `additional_fields` is for custom fields; on v1 all three went in `additional_fields` — see `atlassian-kit:jira-content` § Step 5b.
- **Same `issue-set` on many keys** — `python3 ${CLAUDE_SKILL_DIR}/scripts/acli-issue-set-batch.py KEY1 KEY2 -- --priority High` plans every key and stops at the previews; add `--yes` (before the keys) to apply each. A plan failure aborts before any apply; a failed apply stops the run and lists the keys not attempted.
- **Delete a Jira issue (irreversible, no trash)** — `acli jira workitem delete` has no preview, so use `acli-rest-write.py plan issue-delete --key K` (lists summary, type, status, sub-tasks, link count and warns), then `apply <request> --confirm <12hex>`. One key per run; an issue with sub-tasks is refused unless `--delete-subtasks true`. Prefer transitioning to a cancelled status when it must stay recoverable. Tested against a fake only; no live delete has run.
- **Create a saved filter** (acli has `board create --filter-id` but no filter create) — `acli-rest-write.py plan filter-create --name N --jql J [--description D] [--share-project KEY]`, then `apply <request> --confirm <12hex>`. Without `--share-project` the filter is private to the token's user, so a board on it is invisible to others. Refuses a name that already exists; read-back checks the name and the project share, not the JQL text. Tested against a fake only.
- **Board columns** (no public API sets them) — `acli-rest-write.py plan board-columns-set --board ID --columns '[{"name": "To Do", "statuses": ["To Do", "Open"]}, ...]'`, then `apply <request> --confirm <12hex>`. Uses Jira's internal greenhopper API: the plan reads the board model, resolves status NAMES to ids (refuses an unknown or ambiguous name), overwrites the WHOLE column set (reuses a column's id by name), and prints current vs new columns plus the statuses leaving the board. The PUT payload shape comes from third-party docs and is UNVERIFIED until the first apply: try it on one board and check the UI. Read-back compares column names and status ids via the agile configuration (it ignores order, and a Kanban board may omit an empty Backlog column there, which would report a correct apply as unverified: check the UI).
- **Board delete / property** — `plan board-delete --board ID` (IRREVERSIBLE; Jira keeps the filter and issues; the plan shows name, type and project) and `plan board-property-set --board ID --key K --value '<JSON>'` (documented agile API; the plan shows the old property value). Tested against fakes only.
- **Any other Jira Cloud v3 write** (630 operations, pinned in `skills/ops/data/jira-v3-index.json`) — find the id with `acli-rest-get.py jira-ops component delete` (no request is sent; each row shows method, path, tier), then `acli-rest-write.py plan jira-call --op createComponent --body '{"name": "api", "project": "APPR"}'`; path parameters with `--path id=11`, query parameters with `--query name=value`, a body with `--body JSON` or `--body-file F`. The index checks the operation id, every path and query parameter, enum values and the required top-level body fields before any request. Tiers: `write` runs on plan + confirm; `destructive` (every DELETE, plus admin areas such as workflows, permission and notification schemes, groups, screens, bulk) also needs `--allow-destructive yes`; experimental and deprecated operations need `--allow-experimental yes` / `--allow-deprecated yes`. Reads, multipart uploads, and operations that already have a hand-written entry (issue-set, issue-delete, version-*, filter-create) are refused with a pointer. The read-back confirms a DELETE by a 404, a PUT by comparing the sent scalar fields with the resource, and a create by following the returned `self` link; when none of these can be derived the apply ends "sent but unverified" and you check Jira. Refresh the index with `gen_jira_index.py --fetch` and review the printed added/removed/changed counts.
- **Board reads** — `acli-rest-get.py api jira <path>` accepts `/rest/agile/1.0/board[?query]`, `/board/ID`, `/board/ID/configuration|properties|features`, `/board/ID/properties/KEY` and the internal `/rest/greenhopper/1.0/rapidviewconfig/editmodel?rapidViewId=ID` (it carries status NAMES; the agile configuration has only ids). Not built (internal APIs, payloads unverified): board rename, board filter change, swimlanes, quick filters, card colours, estimation.
- **Priority on an existing issue** — `edit` has no `--priority`; `plan issue-set --key K --priority High`, then apply with the printed `request:` and `confirm:` values (verified live, 2026-11-24).
- **Site-specific status names** — `transition --status` needs the exact name; the write script has no transition operation. List real names with `acli-rest-get.py transitions KEY` first (the mimotech site spells it `Cancled`; no Won't Do/Cancelled/Closed).
- **Epic create stdout may be stubbed by context-mode** — find the new key with `workitem search --jql 'issuetype = Epic AND created >= -1h'`.
- **cloudId** — acli has no cloudId concept at all; it operates against the currently authed site transparently. Every MCP call above needs one. → MCP `getAccessibleAtlassianResources`. Not a capability gap of its own — a prerequisite lookup for every other row here.
- **Create/update a Confluence *page*** — acli `confluence page view` covers reads (including via `--body-format atlas_doc_format` + `${CLAUDE_SKILL_DIR}/scripts/adf2md.py`), blog + space have full acli CRUD, and page create/update route through `${CLAUDE_SKILL_DIR}/scripts/acli-rest-write.py` (`page-create`, `page-delete --page <id>` (to the trash; refuses a homepage or a page with children), `attachment-upload --page <id> --file <png|jpg|gif|svg> [--name N]` (images up to 10 MB, never replaces a name; needs `ACLI_REST_WRITE_CONFLUENCE_FILE_TOKEN`, a classic token with only `write:confluence-file`, because the v1 upload rejects granular tokens), and `page-fetch` + `page-update` with the base-file + confirm-hash flow; ADF body via `${CLAUDE_SKILL_DIR}/scripts/md2adf.py`). First live writes are blocked by site permissions (2026-11-19) — agents stop after the preview. The MCP shapes below stay for when the MCP returns: `createConfluenceContent` / `updateConfluenceContent` (v1: `createConfluencePage` / `updateConfluencePage`). ⚠️ These take a body format of `"html"|"markdown"|"adf"` (v2: `body={"format": ..., "value": ...}`; v1: `contentFormat` + string `body`) — a **different content model from `acli confluence blog create`'s storage-format XHTML.** For a plain doc (headings/lists/bold, no Confluence-specific panels/macros) use the `"markdown"` format with a raw Markdown body — don't hand-write XHTML for a page, that's the blog-only mechanism. Spec/PRD template → `atlassian-kit:confluence-content` § `templates/confluence-spec.md`.
- **Move an issue to a different project** — the one row here with **no MCP fallback either.** `edit --from-json` has no project-move field, and Jira Cloud doesn't expose a project move via the plain edit endpoint — it requires the separate [Bulk Move REST API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-bulk-operations/) (beta), which none of the Atlassian MCP tools available in this plugin wrap. → Jira UI's bulk-move wizard only. Don't attempt this via `editJiraIssue`'s `fields:{project:{...}}` — it isn't a supported path.

## METHODOLOGY

- **Rule 1 (think before coding):** auth-status + JQL-preview before any bulk mutation — `--yes` on a wrong JQL is silent orthogonal damage at scale.
- **Code for judgment:** let JQL deterministically select work items; don't hand-enumerate keys you could query.
- **Fail loud:** `--ignore-errors` off by default; "transitioned 40" must not hide "skipped 12". On a *single* create/edit rejected for an unknown field/label/type, report the exact error — never silently drop the offending field and retry. A dropped field is a silent spec change.
